# 架构设计

> 适用基线：合集仓库 `v0.1`（P1 完成）。桌面端见 [cs-helper-exe](https://github.com/QAQ-AWA/cs-helper-exe)。

## 1. 定位

把「单机版对局助手」拆成三端，解决三件事：

| 痛点 | 现状（单机） | 合并后 |
| --- | --- | --- |
| 重复调用 | 5 个队友各拉一次数据、各调一次大模型 | 服务端一次，广播 5 份 |
| 本机开销 | 边打游戏边解析 100–200MB 的 `.dem` | 解析在服务端，客户端零负担 |
| 信息不共享 | 只有开着客户端的人能看到 | 队友手机进房间即可看 |

**边界**：只处理赛前公开数据与历史 Demo。不读游戏内存、不注入进程、不提供局内实时敌人位置。

## 2. 拓扑

```
┌── PC 客户端（cs-helper-exe）──────────────────────────────┐
│ 5E CDP 侦测 · 完美世界日志解密 · 就绪倒计时 · 本地展示      │
│ 职责：只上报"我看到了什么"，不上报结论                      │
└───────────────┬──────────────────────────────────────────┘
                │ HTTPS 上报（幂等键 platform:matchId）
                │ WSS 订阅（seq 续传）
┌───────────────▼──── server/ ─────────────────────────────┐
│ 房间中心：房间码 / 成员 / 在线态 / TTL                      │
│ 任务编排：按 matchId 全局去重、优先级、并发配额、取消        │
│ 分发：WS 增量事件（指针）+ HTTP 大对象（载荷）              │
│ 计算：engine/（Demo 解析，异步）· AI（P4）                  │
└───────────────┬──────────────────────────────────────────┘
                │ WSS
┌───────────────▼──────────────────────────────────────────┐
│ 手机端（PWA）：房间码加入 · 阵容 · 选手详情 · 轨迹回放 · AI  │
└──────────────────────────────────────────────────────────┘
```

**服务端是房间状态的唯一权威**。这样手机、PC、换设备重进，看到的内容永远一致。

## 3. 关键决策

### 3.1 必须解决的四个冲突

1. **侦测双实现**：上游 Python 版（`fivee_monitor.py` 2260 行）与客户端 Rust 版（`platform_5e_cdp.rs` 998 行）做同一件事。→ 只保留 Rust，Python 版不进服务端（服务端本来也不该连玩家本机 9222）。
2. **上游 Flask 是单例状态机**：模块级 `state` + "已有任务运行则 409" + 全局输出目录，一个进程只能服务一个人。→ 用 FastAPI 重写网关，状态按房间隔离。
3. **协议有客户端无服务端**：`sync-client.ts` 已定义 `/api/v1/room/*`、`/ws?token=` 与 `{action,payload}`，但仓库里没有实现。→ 服务端按现有形状实现，只做加法（`seq`、`snapshot`）。
4. **模型不对齐**：客户端给 `teams.ct/t`，引擎要 `player_hints[{username,domain,steamid}]`。→ 在 `server/app/adapters.py` 一层转换，两侧内部模型都不动。

### 3.2 技术选型

| 决策 | 选择 | 否决 | 理由 |
| --- | --- | --- | --- |
| 网关 | FastAPI + uvicorn | 在 Flask 上加 flask-sock | 需要原生 WS、异步并发、Pydantic 校验；同步+全局锁模型改造成本高于重写路由 |
| 解析引擎 | 复用上游 Python（`engine/`） | 重写 | 1615 行 pipeline + 97 个测试是现成资产 |
| AI 位置 | P1–P3 留客户端，P4 迁服务端 | 立刻上云 | 客户端一次调用已满足"五人共享"；先跑通分发再谈上云 |
| 手机端 | PWA → Capacitor APK | 先做 Flutter/RN | 复用 Vue 组件与渲染核；国内商店分发成本高 |
| 仓库 | 合集 + 子项目分仓 | 单仓混放 | 发版节奏不同，靠契约对齐而非代码复制 |

## 4. 模块归属

| 模块 | 位置 | 说明 |
| --- | --- | --- |
| Demo 检索/下载/解析 | `engine/` | 纯计算，无 HTTP 框架 |
| 房间/编排/分发 | `server/` | 见 `server/README.md` |
| 事件契约 | `contract/events.json` | 与 `server/app/events.py` 互为镜像 |
| 本机侦测 | cs-helper-exe | Rust CDP / 日志解密 |
| 回放渲染 | 待抽为 `replay-core` | 上游 `replay.js` 仅 379 行，PC/手机共用 |

## 5. 契约

- **上传**：`POST /api/v1/match/report?roomCode=`，`Idempotency-Key: platform:matchId`，重复上报只 upsert。
- **事件信封**：`{protocolVersion, seq, ts, action, payload}`。`action` 名称沿用客户端已有实现。
- **传输分工**：WS 只传通知与摘要，大对象走 `GET /api/v1/artifacts/{id}`（ETag + gzip + 按玩家懒加载）。单人回放 JSON 约 140–190KB，五人叠加直接 1MB，走 WS 会拖死手机首屏。
- **断线补齐**：重连带 `lastSeq`，服务端从环形缓冲补发；补不上则发 `ROOM_STATE_SYNC`（含 `profiles` 与 `latestSeq`），客户端据此重置。

## 6. 时延：必须做双档

准备阶段只有数十秒，而 Demo 下载+解析是分钟级。**首次遇到的新对手，轨迹不可能在开局前产出**，这是物理限制，不是优化问题。

| 档位 | 内容 | 目标 |
| --- | --- | --- |
| 实时档 | 侦测 → 上报 → 画像 → AI 流式 | 秒级，必须赶上准备阶段 |
| 深度档 | Demo 发现 → 下载 → 解析 → 轨迹 | 30s–3min，异步落缓存，供本局中途/赛后/下次遭遇 |

产品文案必须写成"稍后推送"，不能承诺"开局即得"。

## 7. 路线图

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 ✅ | 抽离 `engine/`、建契约、冻结 legacy | 引擎测试独立通过 |
| P1 ✅ | 房间、上报、画像广播、WS 续传 | 手机 3s 内看到十人名单；断网 30s 可补齐 |
| P2 | 接引擎：`pipeline.run(player_hints=...)`、artifacts、配额 | 同 matchId 两个房间只解析一次 |
| P3 | PWA：选手详情、轨迹回放、AI 卡、赛后 | 4G 首屏 < 3s |
| P4 | AI 上云：Node worker 复用客户端 TS 实现 | 5 端只产生 1 次大模型调用 |
| P5 | 归档、观测、配额、灰度 | 连续 7 天无 P1 故障 |

P2 的第一件事不是接 pipeline，而是把 `engine/config.py` 的全局 `OUTPUT_DIR` 按 job 隔离——否则并发任务会互相覆盖 `player_{domain}.json`。

## 8. 风险

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| 合规红线（被认定为局内情报） | **高** | 只做赛前历史数据；不读内存/不注入；轨迹只展示历史习惯 |
| 平台 ToS 与反爬 | 高 | 抓取集中在 `api_client` 便于替换；低 QPS + 缓存优先；失败降级 |
| 平台接口变更 | 高 | 侦测层版本化 + 契约测试 + 灰度 |
| 时延不达标 | 高 | 双档交付；画像/AI 优先；文案预期管理 |
| 单例改造回归 | 中 | 先抽 `AnalysisJob` 再改内部；黄金样本比对 |
| 双端模型漂移 | 中 | 契约镜像 + 测试守护 + `protocolVersion` |
| 个人信息（PIPL） | 中 | 只收公开战绩；最小化；留存期与删除接口 |
